# Авторизация и безопасность

## Вход и регистрация

- Вход по логину и паролю. Логины в нижнем регистре (`[a-z0-9._-]{3,32}`), пароль от 8 символов, хеш — **bcrypt**.
- **Открытой регистрации нет.** Первый администратор создаётся скриптом (`npm run user:create … --admin`), остальные — только по приглашению:
  1. админ создаёт приглашение (`POST /invites`) и отправляет ссылку `…/invite/<token>`;
  2. ссылка одноразовая и живёт 7 дней; в базе хранится только **sha256 токена**;
  3. коллега открывает ссылку, фронт проверяет её (`GET /auth/invite/:token`), регистрация (`POST /auth/register`) сразу выполняет вход.
- Админ видит и отзывает только свои приглашения.

## Токены

| | Access | Refresh |
|---|---|---|
| Что | JWT | непрозрачная строка `sessionId.secret` |
| Срок | 15 минут | 90 дней, скользящий |
| Где | `httpOnly; Secure; SameSite=Strict` кука | такая же кука с `Path=/api/auth/refresh` |
| На сервере | — | в таблице `sessions` — sha256 секрета, по сессии на устройство |

- Токены недоступны JavaScript (`httpOnly`) — XSS не может их украсть.
- `SameSite=Strict` и один домен для фронта и API защищают от CSRF.
- Refresh-кука уходит только на `/api/auth/refresh`, а не с каждым запросом.

### Ротация и обнаружение кражи

При каждом обновлении выдаётся новый refresh, старый становится недействительным. Если кто-то предъявляет **уже использованный** refresh (совпал `sessionId`, но не хеш секрета), это значит, что токен скопировали: сервер удаляет **все сессии пользователя** на всех устройствах.

На клиенте (`frontend/src/api/client.ts`) обновление токена выполняется **одно на все параллельные запросы**: иначе второй запрос предъявил бы уже использованный refresh, и защита от кражи разлогинила бы пользователя.

### Выход

Refresh-кука на `/auth/logout` не приходит (из-за `Path`), поэтому сессия для удаления берётся по `sid` из access-JWT: подпись проверяется, истечение — нет (выйти можно и с просроченным access).

## Доступ к данным

- Глобальный `JwtAuthGuard` (токен из куки) на всех маршрутах; открытые маршруты помечены декоратором `@Public()`.
- Админские маршруты дополнительно проверяет `AdminGuard` — по флагу `isAdmin` в базе, а не в токене.
- Все данные привязаны к `userId`, каждый запрос фильтруется по текущему пользователю.
- Входные данные проверяются DTO с `class-validator` (длины строк, форматы дат, коды препаратов).

## Секреты и персональные данные

- Секреты сервера (пароль базы, ключ подписи JWT) — только в `.env` на сервере, в репозиторий не попадают; в git лежат образцы `.env.example`.
- Ключ выкладки и ключ подписи APK — в секретах GitHub Actions.
- Реальные Excel-файлы и дампы базы содержат персональные данные врачей (ФИО, телефоны) — они исключены `.gitignore` и в репозиторий не попадают никогда.
